# 개인·프로젝트 작업공간 구현 계획

2026-10-21 · APP-REQ-015~019 / AC-30~34

[제품 비교와 기능 기획](../planning/12-task-workspace-benchmark.md)을 실행 단위로
옮긴다. Projects의 요구·문서·SkillRun·테스트 관계는 유지하고, 개인 일정
관리와 프로젝트 구현 관리를 같은 작업 목록에서 제공한다. 산출물 본문은
[Note 연계 전 임시 Markdown 범위](note-document-handoff.md)에 머문다.

## 데이터와 완료 계약

작업은 기존 `Item(kind=task)` ID·revision·관계를 사용하고 PostgreSQL의
JSON 데이터에 `workflow`, 목록, 실행 예정일·마감일, 예상 소요, GTD 속성,
ABC 등급·순서·목표, GitHub Issue URL을 저장한다. 기존 작업에서 `workflow`가
없으면 `delivery`로 해석해 완료 근거 검사를 그대로 적용한다. 생성 후
`workflow` 변경은 409로 거부한다. `personal` 작업은 한 줄 제목으로 만들고
완료할 수 있지만 선행 작업이 있으면 모두 완료되어야 한다. `delivery`는
수용 조건·결과 URL·필요한 현행 테스트/commit SHA가 있어야 완료할 수 있다.

날짜는 빈 값 또는 ISO `YYYY-MM-DD`만 허용한다. 예상 시간과 ABC 그룹 내
순서는 음수가 될 수 없다. GitHub 링크는 `https://github.com/owner/repo/issues/n`
형식만 저장한다. 외부 Issue 내용·상태·권한을 읽었다고 표시하지 않는다.
작업 저장은 기존 `expected_revision` 동시 수정 검사를 사용한다.

## 화면과 상태 계산

작업 메뉴의 진입점은 `?view=tasks`다. `taskMode=simple|complex`와
`taskView`는 URL의 보기 상태일 뿐 별도 작업 데이터가 아니다. `item`은
같은 상세 대상을 가리킨다. 전역 21개 pydemia UI 모드와 light/dark 테마는
보기 밀도와 독립이다. 버튼·입력·라벨·배지·빈 화면·알림은 편입한
`ui.pydemia.ai` 컴포넌트/토큰을 사용한다.

| 간편 보기 | 계산·행동 |
|---|---|
| 오늘 | 실행 예정일이 브라우저 로컬 오늘이거나 마감이 오늘/지난 열린 작업. 기본 빠른 입력 날짜는 오늘 |
| Inbox | 목록 이름이 `Inbox`인 열린 작업. 오늘과 중복 표시 가능하나 같은 ID |
| 예정 | 미래 실행 예정일 또는 실행일이 없고 미래 마감인 열린 작업 |

간편 화면의 빠른 입력은 `personal` 작업을 만들고 개인 작업은 체크로 완료한다.
기존 구현 작업을 체크하면 정교 상세 화면에서 완료 근거를 입력하도록 연다.
완료 항목의 다시 열기는 정교 목록에서 상태를 전체로 본 뒤 수행한다.
작업 상세의 별도 유형 옵션은 생성 시 선택하고 변경할 수 없게 한다.

정교 화면은 목록·상태 보드·월간 캘린더·집계를 제공한다. 검색·상태 조건을
공통 작업 집합에 적용한 뒤 보기만 바꾼다. 캘린더는 실행 예정일과 마감일을
같은 날짜에 표시하며 날짜 없는 작업은 목록에 남긴다. 집계 막대는 현재
필터의 상태·마감 경과·ABC 분포와 열린 작업의 예상 시간을 합산한다.
이력 시계열이나 실측 시간을 나타내지 않아 `현재 스냅샷`으로 표기한다.
보드는 읽기/상세 열기부터 제공하고 드래그 상태 변경은 후속이다.

GTD 보기 정렬은 다음 행동 표시, 선택한 맥락·가용 시간·에너지 적합성,
마감일을 순서대로 고려한다. 조건에 맞지 않는 작업도 숨기지 않고 뒤에
둔다. ABC 보기는 A→B→C→미지정, 그룹 내 번호, 마감일 순이다. 두 기준은
독립 필드이므로 보기 전환이 저장된 우선순위를 자동 수정하지 않는다.

## 검증과 단계

1. 모델/서버: `TaskData` 검증과 완료 분기, 기존 delivery 호환·유형 변경
   차단을 PostgreSQL 전용 schema 통합 테스트로 검사한다. 임시 SQLite
   경로를 만들지 않는다.
2. 웹: 간편 입력·개인 완료·같은 항목의 보드/집계 반영과 GTD/ABC 정렬,
   캘린더 날짜를 Vitest로 검사한다. TypeScript·Vite 빌드를 통과시킨다.
3. 브라우저: 실제 로그인 세션에서 간편/정교 전환, 상세 편집, URL 재방문,
   light/dark·모바일 폭을 본다. mock 화면 검사와 실제 운영 검사를 구분한다.
4. 배포: source archive의 비밀 제외·favicon 포함을 확인하고 기존
   PostgreSQL volume을 보존한 채 앱 이미지를 교체한다. 건강 상태와
   로그인 후 작업 화면을 재확인한다.

현재 구현은 1~4단계의 첫 범위를 포함한다. 검사 결과와 운영 브라우저
판정은 [검증 기록](verification.md)에 구분해 남긴다.

## 후속 설계 계약

GitHub Issue의 읽기·쓰기 연동은 별도 OAuth 권한, 프로젝트/저장소 매핑,
비공개 Issue 접근, webhook 서명·중복·역순·재동기화, 사용자 수정과 원격
수정 충돌, 연결 해제·토큰 폐기를 정의한 뒤 시작한다. URL 링크는 Issue
완료나 Projects 작업 완료를 의미하지 않는다.

반복·알림·시간 실측·타이머는 사용자 시간대와 반복 인스턴스 식별,
알림 권한, 이력/삭제 정책이 필요하다. 다중 작업 편집·저장 필터·드래그
보드·Gantt·작업량·추세 그래프는 필터 저장 위치, 상태 변경의 완료 gate,
시간 이력 스키마를 먼저 정한다. 개인 전 프로젝트 Today는 프로젝트별
권한을 유지한 집계 API를 설계한 후 확장한다.
