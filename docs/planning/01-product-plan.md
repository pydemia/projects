# 기능 기획

상태: 제안 · v0.3 · 2026-10-21

## 목적과 사용자

스킬을 활용하는 LLM이 메모를 요건화하고 문서·계획을 작성·수정·검수한다. 개인 개발자가 메모를 실행 가능한 프로젝트로 구체화하고, 소규모 팀이 그 근거와 결과를 이어받을 수 있게 한다. 프로젝트를 다시 열었을 때 현재 범위, 최근 결정, 진행 중인 작업, 검증되지 않은 부분을 파악할 수 있어야 한다.

초기 주 사용자는 기획·설계·개발을 겸하는 개인이다. 이후 소규모 팀의 기획자·개발자·검토자가 같은 요구사항과 산출물을 연결해 작업한다. 고객 유형·유료화·기업용 SI 도입은 아직 검증하지 않은 사업 가설이다.

현재 참고 문서는 기획, 설계, 개발, 테스트, 운영, 보고의 산출물을 나눈다. 앱에서는 문서의 종류와 해당 문서가 다루는 기능·작업·검증 대상을 함께 관리한다. 원문에 나열된 모든 문서를 모든 프로젝트에 의무화하지 않는다.

## 대표 사용 시나리오

| 상황 | 사용 순서 | 사용자가 확인하는 결과 |
|---|---|---|
| 새 아이디어 구체화 | 아이디어 메모 → 프로젝트 전환 → 목표·사용자·범위 정리 → 요구사항 작성 | 원문을 보존한 기획서와 식별자가 있는 요구사항 |
| 기능 설계 | 요구사항 선택 → 화면·앱·인터페이스 설계 연결 → 미정 사항 기록 | 구현에 필요한 설계와 미해결 결정 |
| 개발 시작 | 확정한 범위 선택 → 작업 분해 → 의존성·완료 기준·테스트 연결 | 바로 착수할 수 있는 작업 목록 |
| 아이디어 반영 | 메모 → 요건 후보 → 기존 기능 대조 → 변경 묶음 | 요건·설계·작업·회귀 테스트 초안과 원안 연결 |
| 단일 문서 작업 | 파일·요청·스킬 선택 → 작성/수정/검수 | 앱 밖에서도 같은 스킬 bundle로 다룰 수 있는 문서 |
| 변경 발생 | 요구사항 새 리비전 작성 → 변경 확정 → 영향 대상 검토 | 재검토할 문서·작업·테스트와 사유 |
| 완료 판단 | 작업 결과·commit·테스트 실행 기록 → 기준선 점검 | 근거가 있는 완료 / 근거 누락 / 예외 승인 구분 |
| 협업·인계 | 문서·결정·리스크·산출물 묶음 조회 | 다른 사람이 이어서 작업할 수 있는 프로젝트 기록 |

예를 들어 “문서 이력 복구” 요구사항을 “승인 이력까지 복구”로 바꾸면 앱 설계, 해당 구현 작업, 복구 테스트가 영향 후보로 표시된다. 원래 확정된 문서와 통과한 테스트 기록은 보존하고 새 기준에 대한 검토 상태를 별도로 표시한다.

## 정보 단위와 관계

| 단위 | 주요 필드 | 관계 |
|---|---|---|
| Project | 이름, 목표, 범위, 프로필, 소유자, 상태 | 모든 업무 객체의 경계 |
| Idea | 원문, 출처, 가설, 질문, 보류 이유 | 0개 이상의 요구사항·프로젝트로 구체화 |
| Feature | 기능 ID, 현재 동작, 구현·명세 근거 revision | 요건·화면·코드·테스트와 아이디어의 반영 대상 |
| SkillRun | 요청, bundle lock, 입력, 도구, 결과, 검수, 상태 | 생성·수정한 문서와 변경 묶음 |
| Requirement | ID, FR/NFR, 내용, 수용 조건, 우선순위, revision | 설계·작업·테스트의 기준 |
| Artifact | 유형, 제목, 본문/외부 링크, 담당, revision, 검토 상태 | 요구사항과 다른 산출물 참조 |
| Task | 범위, 담당, 상태, 의존 작업, 완료 기준 | 기준 문서·요구사항·변경 결과·테스트 연결 |
| TestCase / TestRun | 절차·기대 결과 / 실제 결과·환경·대상 revision·증빙 | 케이스와 실행 이력을 분리 |
| Decision / Change | 선택·대안·이유 / 변경 전후·영향·판정 | 관련 revision과 후속 조치 |
| Baseline / Release | 범위, 확정한 revision 목록 / 대상 commit·실행 결과 | 시점별 합의와 검증 근거를 고정 |

관계는 다대다를 허용한다. `근거`, `구현`, `검증`, `의존`의 의미를 구분한다. 문서 안에 링크만 붙이는 것과 “이 테스트가 이 요구사항을 검증한다”는 구조화된 관계는 별개다. 요구사항 표와 요구사항 정의서의 내용은 같은 데이터에서 표시해 중복 수정하지 않는다.

## MVP 기능 요구사항

MVP-A는 단일 문서의 스킬 기반 작성·수정·검수와 앱 밖 작업을 완주하는 버전이다. MVP-B는 아이디어 요건화·기존 기능 연결·설계/작업/검증 반영을 통합한 첫 프로젝트 제품이다. 두 버전에 LLM 작업을 포함한다.

| ID | 기능 | 범위와 동작 | 수용 기준 |
|---|---|---|---|
| FR-01 | 프로젝트 생성 | 이름·목표·간편/표준 프로필, 기본 단계·문서 목록 제안 | 생성 직후 메모 작성과 필수 산출물 확인 가능 |
| FR-02 | 아이디어 관리 | 메모·링크·질문, 프로젝트 전환·보류·원문 보존 | 전환 후에도 원안과 전환 이력을 조회 |
| FR-03 | 기능·비기능 요구사항 | ID, 수용 조건, 우선순위, 범위, revision, 제외 사유 | 동일 ID의 변경 전후를 비교 |
| FR-04 | 산출물 작성 | Markdown 본문, 표·Mermaid, 템플릿, 외부 파일/URL 등록 | 요청한 7종 문서를 생성·저장·재열람 |
| FR-05 | 버전과 검토 | 초안 저장, 검토 요청, 변경 요청, 확정, 과거 버전 복원 | 확정본을 덮어쓰지 않고 새 리비전 생성 |
| FR-06 | 구현 계획과 작업 | 요구사항·문서 선택, 작업·선행 관계·완료 조건 작성 | 순환 의존을 막고 착수 가능 작업 표시 |
| FR-07 | 테스트와 증빙 | 케이스, 실행 결과, 대상 revision·환경·로그/링크 | 실행 안 함과 성공을 구분하고 과거 결과 유지 |
| FR-08 | 추적과 변경 영향 | 요구사항별 설계·작업·테스트 연결, 근거 revision 고정 | 변경 확정 시 영향 후보와 경로 제시 |
| FR-09 | 현황과 완료 점검 | 작업·산출물·검증 상태, 누락·재검토·막힘 목록 | 전체 완료와 부분 완료를 구분 |
| FR-10 | 검색과 반출 | 프로젝트 내 제목/ID/본문 검색, Markdown·JSON·파일 manifest ZIP | 내보낸 묶음으로 범위·revision·관계 확인 |
| FR-11 | AI 문서 초안 | 선택한 메모·요구사항으로 템플릿 초안·질문 생성 | 출처와 미확인 가정을 표시하고 검토 후 채택 |
| FR-12 | AI 계획·누락 점검 | 작업·테스트 후보와 빠진 항목 제안, 선택 적용 | 기존 내용 보존, 취소 가능, 자동 확정 금지 |
| FR-13 | 기존 기능 기준 | 기능 ID·현재 동작·화면/API/코드 근거·revision | 관찰 사실과 추정 기능 구분, 기존 요건 역추적 |
| FR-14 | 아이디어 요건화·기능 대조 | 신규/확장/변경/통합/중복/충돌/보류 제안 | 후보별 출처·수용 조건·영향·사용자 결정 보존 |
| FR-15 | 구현 반영 묶음 | 요건·설계 수정·작업·의존·회귀 테스트 초안 | 선택한 변경 연결, 확정본 보존, 중복 적용 방지 |
| FR-16 | 스킬 resolve·고정 | Hub bundle 원문·hash·참조·실행 lock | 요약 규칙으로 대체하지 않음, 진행 중 업데이트 금지 |
| FR-17 | 문서 독립 실행 | 문서 한 개와 스킬·자료로 앱 안/밖 작성·수정 | 앱 DB 없이 사용, 실행 묶음 반출과 외부 diff 재연결 |
| FR-18 | LLM 작업 세션 | 요청·근거·도구·문서 변경·질문·검수·재개 | 미완료·실패·취소 보존, 허용 범위에서 계속 수행 |
| FR-19 | 산출물 양식·예시 참조 | 원문 35종 유형과 7종 필수 문서 매핑, 프로젝트 양식·공개 보완 자료 선택, 확인 상태·버전·출처 manifest | 실제 사용한 양식·예시를 스킬 규칙과 구분하고 앱 밖 전달·재연결; 접근 실패·미확인 보존 |

MVP-A는 FR-04·05·10·11·16~19의 단일 문서 흐름을 우선한다. MVP-B에서 FR-01~19의 프로젝트 통합 흐름을 제공한다. MVP-A에서도 GitHub PR·commit·CI 결과의 URL과 SHA를 수동으로 등록한다. 파일은 업로드본의 revision·크기·해시·매체 유형을 기록하며 편집기는 외부 Office·Figma 파일의 본문 편집을 맡지 않는다.

FR-19는 [산출물 조사](10-reference-audit.md)와 [양식 라이브러리](11-template-reference-library.md)를 실행에 연결하는 기능이다. 기존 문서·프로젝트 지정 양식을 우선하며, 원본이 없거나 접근할 수 없을 때 확인된 공개 자료·자체 시작 양식을 제시한다. 외부 양식이 스킬 원문을 대체하거나 국소 수정 대상의 형식을 강제로 바꾸지 않는다. 35종은 선택 가능한 분류이며 모든 프로젝트의 필수 작성 목록이 아니다. 상세 작업과 검증은 [구현 계획](04-delivery-and-tests.md)에 둔다.

## 단계·상태·완료 규칙

프로젝트의 생명주기, 문서의 검토 상태, 작업 상태, 최신성은 서로 다른 필드다. “설계 단계”에 있다고 구현 작업을 막지 않는다. 범위 또는 마일스톤별 기준선을 만들어 반복 진행한다.

| 대상 | 상태 |
|---|---|
| 아이디어 | 수집 → 검토 → 프로젝트화 / 보류 / 제외 |
| 문서 revision | 초안 → 검토 중 → 확정 / 수정 요청; 초안에서 보관 가능 |
| 작업 | 할 일 → 진행 중 → 검토 중 → 완료; 막힘은 별도 사유·속성 |
| 테스트 실행 | 실행 중 → 통과 / 실패 / 중단; 실행 기록 없음은 미실행 |
| 영향 검토 | 미검토 → 영향 있음 / 영향 없음(사유) → 조치 완료 |
| 프로젝트 | 준비 → 진행 → 완료 / 보관 |

확정은 특정 revision에 대한 기록이다. 확정본에서 편집하면 다음 초안을 만들고 확정본은 계속 조회할 수 있다. 과거 버전 복원도 새 초안 생성으로 처리한다. 초안 편집 중 영향 후보를 미리 보여 줄 수 있으나 완료 지표를 바꾸는 것은 변경 확정과 새 기준선 지정 이후다.

“재검토 필요”는 확정 여부와 독립된 표시다. 기준 요구사항 v2가 확정되어도 기존 v1 기준 설계·테스트의 역사적 효력을 삭제하지 않는다. v2를 채택한 현재 범위에서 재검토·재실행해야 함을 표시한다. 순환하는 일반 참조는 방문 집합으로 탐색을 종료하고, 선후행 작업의 순환은 등록 단계에서 거부한다.

### 완료 조건

- 작업 완료: 명시한 수용 조건 충족, 결과물 연결, 해당 작업에 요구되는 테스트 근거, 미해결 차단 사유 없음. 코드 변경이 없는 문서 작업에는 PR을 강제하지 않는다.
- 마일스톤 완료: 범위 내 필수 산출물의 해당 revision 확정, 요구사항별 설계·구현·검증 연결, 해당 기준선에서 유효한 테스트, 미해결 차단 결함 없음.
- 프로젝트 완료: 선택한 마일스톤 완료와 종료 보고/인계 묶음 생성. 배포가 범위이면 배포 결과도 포함한다.
- 예외: 비적용 사유 또는 위험 수용자·시점·범위·후속 조치를 기록한다. 엄격 모드에서 수용 불가한 조건을 별도로 정의한다.
- 개인 모드: 소유자가 자기 검토 후 확정 가능하며 자기 확정임을 기록한다. 팀 모드의 독립 검토 정책은 협업 확장 시 적용한다.

진척을 단일 점수로 합산하지 않는다. 작업 완료율은 현재 범위의 취소되지 않은 말단 작업을 분모로 계산한다. 산출물 확정률은 프로필에서 요구한 필수 산출물이 분모다. 검증 충족률은 현재 기준선의 필수 요구사항 중 유효한 통과 근거를 충족한 요구사항 비율이다. 표본 0은 `해당 없음` 또는 `미정의`로 표시한다. 실패·차단·재검토 수를 비율 옆에 함께 보여 준다.

## AI 문서·계획 보조

사용자가 문서 또는 프로젝트와 참조 범위를 선택하면 스킬을 사용하는 LLM 세션으로 실행한다. 문서 단독 작업에는 프로젝트 등록을 요구하지 않는다. 상세 실행·독립성 계약은 [08 문서](08-skill-runtime-and-portability.md)를 따른다. 기본 작업은 “기획서 초안”, “설계 목차와 질문”, “작업 분해”, “테스트 후보”, “누락 점검”이다. 외부 자료는 별도 입력 근거로 표시하고 자료 속 명령이 프로젝트 정책을 바꾸지 못하게 한다.

입력은 사용자가 선택한 revision·문서 섹션으로 제한한다. 결과에는 참조 ID, 가정, 미정 질문, 제안 본문을 구분한다. 근거가 없는 API·일정·완료 사실을 확정 내용으로 만들지 않는다. 의미가 바뀌는 제안은 변경 전후와 항목별 채택·수정·버림을 제공한다. 이미 허용한 문서 작성·국소 수정은 스킬 규칙에 따라 계속하며 단계마다 재승인을 요구하지 않는다. 적용 전 선택만 한 상태와 실제 저장 상태를 구분한다.

스킬 bundle ID·source revision·hash·실제 참조 파일·모델·프롬프트 버전·입력 revision·실행 상태·비용 정보(제공 가능 시)를 기록한다. 프로젝트별 예산, 실행별 입력 한도, 취소·타임아웃·재시도를 둔다. 참조 문서가 바뀌면 재생성하거나 이전 기준 제안으로 표시한다. AI 장애 시 작성 중인 문서와 수동 업무는 계속 사용할 수 있어야 한다. 코드 실행·PR 생성·merge·배포는 이 범위에 포함하지 않는다.

## 품질 목표와 성공 확인

초기 제품 검증은 실제 개인 프로젝트 하나를 이 앱으로 관리하면서 수행한다. 새 요구사항에서 테스트 결과까지 연결할 수 있는지, 며칠 뒤에도 근거를 찾아 작업을 재개할 수 있는지, 요구 변경 후 재검토 대상을 놓치지 않는지 관찰한다.

서버 확인 전 “저장됨” 표시 금지, 충돌 시 초안 보존, 모든 조회·검색·다운로드의 프로젝트 권한 검사, 키보드 조작과 색상 외 상태 레이블을 MVP 수용 조건으로 둔다. 성능·가용성·복구 수치는 배포 방식과 예상 데이터량을 결정한 뒤 실측 기준과 함께 확정한다. 현재 달성률이나 사용자 효과를 측정한 상태는 아니다.
