## 개발 순서

첫 검증 단위는 **문서 한 개를 같은 스킬로 앱 안/밖에서 작성·수정·검수**하는 흐름이다. 실제 Hub bundle을 읽고, 문서·입력 hash·스킬 lock·검수 결과를 남긴다. 이어서 아이디어를 요건화하고 기존 기능·설계·작업·회귀 테스트에 반영한다.

| 단계 | 구현 범위 | 선행 조건 | 종료 기준 |
|---|---|---|---|
| 0. 계약 확정 | 요구 기준·스킬/문서/실행 계약·참조 registry·권한·A-02 수정 | 이번 기획 검토 | APP-REQ-001~009와 첫 실행 수용 조건 확정 |
| 1. 단일 문서 실행 | Hub resolve·hash/cache/lock, 양식·예시 선택, LLM runner, 작성·국소 수정·검수 | 실행 capability와 공급자 결정 | 한 문서의 원문 규칙·선택한 참조·보존·검수 확인 |
| 2. 독립 사용·재연결 | 일반 파일·sidecar·실행 묶음과 참조 manifest, 외부 수정 diff·충돌·revision | 단계 1 | 앱 없이 같은 bundle·참조 사용, 외부 결과 재연결 |
| 3. 아이디어 반영 | 메모·기능 기준·요건화·충돌/중복·변경 묶음 | 단계 1~2, 프로젝트 경계 | 요건·설계·작업·회귀 테스트 연결 초안 생성 |
| 4. 프로젝트 관리 | 작업·테스트·추적·기준선·변경 영향·검색·반출 | 단계 3 | 기준선별 달성·미착수·미검증과 실행 근거 구분 |
| 5. 소규모 팀·연동 | 초대·역할·댓글, GitHub 읽기 동기화 | MVP 사용 검증 | 권한과 동기화 회귀 기준 충족 |

단계 1~2가 MVP-A, 단계 4까지가 프로젝트 통합 MVP-B다. AI·LLM 실행은 처음부터 포함한다. 단계 5는 후속 확장이다. 각 단계에서 해당 요구의 기획·설계·계획·실행 근거를 구분해 검증한다.

일정은 투입 시간·기술 숙련도·호스팅·편집기 선택이 정해지지 않아 아직 확정하지 않는다. 단계 1의 실제 소요와 결함을 바탕으로 나머지 일정을 다시 산정한다. 임의의 주차와 인원으로 납기를 약속하지 않는다.

## 산출물 양식·예시의 구현 범위

[원문 35종 확인 결과](10-reference-audit.md), [공개 양식 라이브러리](11-template-reference-library.md), [참조 registry](references/artifact-templates.json), [자체 시작 양식](forms/)을 DEV-R1~R3의 초기 입력으로 사용한다. 이후 registry 검증·선택 manifest·실행 연결을 구현했다. 실제 검사와 도구 한계는 [검증 기록](../implementation/verification.md)을 따른다.

MVP-A에서는 35종의 유형·출처·확인 상태를 등록하고, 최초 요청한 7종 문서의 신규 작성·국소 수정·검수에 양식·예시를 연결한다. MVP-B에서는 프로젝트 프로필의 생성/비적용 선택과 요건·작업·테스트 추적에 연결한다. 35종을 모든 프로젝트에서 의무 작성하거나 모든 파일 형식의 편집기를 먼저 구현하는 범위로 해석하지 않는다. 초기 작성 형식은 Markdown·Mermaid·HTML 시안이며, 외부 DOCX·XLSX·Figma 자료는 참조·파일 등록부터 지원한다.

실행 시 기존 문서와 프로젝트 지정 양식을 먼저 확인한다. 원본이 없거나 접근할 수 없으면 확인된 공개 보완 자료와 자체 시작 양식을 제시하고, 실제 선택·사용한 자료를 기록한다. 인터넷 양식 조사는 이번 기획에서 수행한 작업이다. 앱의 검색 도구는 요청 범위와 실행 권한이 있을 때 사용하며, 기본 동작에 상시 수집·자동 갱신을 추가하지 않는다.

스킬 원문은 작성 규칙, 양식은 구조 입력, 예시는 참고 자료로 구분한다. 참조 manifest는 `template_ref`, `template_version`, `example_refs`, `inspection_status`, `project_source_refs`를 담고 실제 읽은 자료와 실패 기록을 실행 이력에 연결한다. 프로젝트 비공개 예시를 공용 양식으로 복제하지 않는다. 앱 밖 실행에는 같은 manifest와 허용된 파일·접근 가능한 참조를 전달하고, 접근 불가는 부분 수행으로 남긴다.

## 테스트 전략

공통 UI 개편은 `ui.pydemia.ai` 소스 revision과 선택 컴포넌트의 라이선스·의존성을 기록한 뒤 적용한다. 화면 검사는 Basic light/dark, 형태가 다른 UI 모드, dark 전용 모드, 저장 후 재방문, 주요 업무 흐름과 모바일 폭을 구분한다. favicon은 `web/dist`의 실제 SVG bytes·head 링크와 배포 URL의 Content-Type·응답 hash·브라우저 탭 표시를 각각 확인한다. 빌드 통과만으로 운영 화면 또는 favicon 배포를 통과 처리하지 않는다.

상태·기준선·권한처럼 결과에 영향을 주는 규칙은 단위와 DB 통합 테스트로 확인한다. 사용자 흐름은 소수의 중요한 E2E로 연결하고 외부 AI·GitHub의 정상/실패는 adapter 계약 테스트로 분리한다. 정적 검사 통과만으로 업무 흐름의 완료를 판정하지 않는다.

| AC-23 | 외부 변경 재연결 | 앱·외부에서 같은 기준 파일을 다르게 수정 | 변경 비교·충돌 처리, 기존 ID·출처 보존 |
| AC-24 | 도구 한계·재개 | 필요한 render 도구 없음 또는 worker 중단 | 미검수/부분 수행 기록, 재개 시 중복 변경 방지 |
| AC-25 | 유형·참조 registry | 원문 35종·필수 7종 매핑, 중복 ID·없는 source ID·버전 누락 | 정상 매핑은 조회 가능, 잘못된 참조 거부; 35종 모두 필수 생성으로 처리하지 않음 |
| AC-26 | 참조 상태·보완 | 원본 없음·404·권한 실패·빈 페이지·도식 미확인 | 상태와 확인 시점 구분, 접근 가능한 보완 자료 선택; 보완 성공을 원본 확인으로 표시하지 않음 |
| AC-27 | 양식·예시의 실행 사용 | 필수 7종별 선택 참조와 고정 bundle로 작성, 기존 문서는 국소 수정 | 실제 읽은 참조 기록, 원문 스킬·보존 범위 준수; 예시 수치를 프로젝트 사실로 복제하거나 양식을 강제 교체하지 않음 |
| AC-28 | 참조 manifest 왕복 | 앱 밖 반출·수정·재연결, 고정 자료의 변경/접근 실패 | 양식 버전·예시 출처·기준 hash 유지, 누락/변경 명시; 최신 자료로 조용히 대체하지 않음 |
| AC-29 | 비공개 예시 경계 | 타 사용자·타 프로젝트 예시를 조회/LLM 입력/공용 등록/반출에 사용 시도 | 무권한 내용·첨부·자격증명 비노출, 공용 자료로 자동 전환되지 않음 |

MVP-A에서는 AC-02·03·09·10~15·20~29 중 단일 문서·파일·실행 계약과 개인 접근 경계에 해당하는 조건을 검증한다. AC-27은 필수 7종 각각에 대해 확인한다. 프로젝트 통합 MVP-B에서 AC-01~15·17~29를 검증한다. AC-16은 후속 연동 출시 시 필수이며, 팀 확장 시 AC-09·29를 역할별로 다시 확인한다. 기준선·대상 commit·환경·명령·실행 시점·결과·미실행 사유를 검증 기록에 남긴다.

## 배포와 제품 검증

실제 개인 프로젝트 하나로 단계 1~4를 사용하며 매번 외부 문서로 돌아가야 하는 지점, 중복 입력, 잘못된 완료 표시, 놓친 영향 대상을 기록한다. 첫 릴리즈 기준은 업무 흐름 완주, 중요 규칙 검사 통과, 알려진 결함·위험 기록, 백업 복원 확인이다.

자동 배포·운영 권한과 관련 없는 작업을 포함하지 않는다. 앱의 배포는 별도 실행 단계이며 이번 기획 결과로 서비스가 배포된 상태는 아니다. 운영 데이터 변경이나 AI 기반 코드 실행 기능도 아직 구현하지 않는다.

## 이번 산출물의 검증 범위

이 문서의 개발 단계와 AC는 초기 계획이다. 이후 구현한 실제 앱의 판정은
[요구사항 현황](09-requirements.md)과 [검증 기록](../implementation/verification.md)에
남긴다. 문서 확정·고급 이력 UI는 최신 Note 연계 결정에 따라 후속 범위로
조정했다. 초기 HTML 시안의 검사와 실제 앱의 검사를 혼동하지 않는다.
