# 산출물 카탈로그

상태: 프로젝트 템플릿 제안 · v0.2 · 2026-10-21

## 프로필

간편 프로필은 개인·작은 프로젝트용이다. 기획서 안에 기능·UI 섹션을 두고, 하나의 설계서에 System·Infra·Application·Interface 섹션을 둬도 된다. 구현 계획·테스트 계획과 결과는 필요한 구조화 데이터에서 생성한다. 문서 개수와 관계 추적의 정밀도를 혼동하지 않는다. 모든 작성·수정·검수는 선택한 Hub 스킬 원문과 필요한 참조를 사용한다. 템플릿은 목차·입력 구조이며 스킬 규칙을 별도 복제하지 않는다.

표준 프로필은 단계별 산출물과 담당·검토가 필요한 프로젝트용이다. 사용자 요청의 일곱 종류를 독립 문서로 만들고 요구사항·테스트·변경 기록을 연결한다. 프로필은 기본 목록이며 사용자가 필수·선택·비적용을 조정할 수 있다. 비적용은 사유를 남기고 과거 기준선의 목록을 소급 변경하지 않는다.

## 핵심 문서의 경계와 작성 항목

| 유형 | 작성 항목 | 연결 대상·완료 조건 |
|---|---|---|
| 아이디어 메모 | 원문, 문제, 대상 사용자, 가설, 출처, 질문 | 파생 요구사항·전환 이력; 원문 보존 |
| 기능 기획서 | 목적, 사용자, 범위/제외, 사용 시나리오, FR/NFR, 우선순위, 수용 조건 | 요구사항 원본 표; 각 필수 기능의 완료 조건 |
| UI 기획서 | IA, 화면 목록/ID, 진입·이동, 레이아웃, 조작, 정상·빈·오류·권한·반응형 상태, 시안 | 요구사항·화면·인터페이스; 주요 흐름 검토 |
| System Architecture | 시스템 경계, 사용자/외부 시스템, 구성 요소, 주요 데이터 흐름, 품질 목표, 대안·결정 | NFR·Application·Infra; 경계와 책임 일치 |
| Infra | 환경, 배포 단위, 네트워크, 접근/secret, 저장·백업, 관측, CI/CD, 복구 | 시스템 구성·운영 요구; 배포/복구 검증 계획 |
| Application | 모듈 책임, 데이터/ERD, 도메인 규칙, 상태 전이, 트랜잭션, 비동기·오류·권한 | 기능·작업·DB migration; 구현 가능한 규칙 |
| Interface | 생산자/소비자, API·이벤트·파일, 입출력 schema, 인증, timeout, 재시도·멱등성, 오류·버전 | 화면·모듈·외부 연동; 계약과 테스트 |
| 구현 계획서 | 범위/기준선, 마일스톤, WBS·작업, 의존성, 담당·견적, 완료 조건, 검증·배포 순서, 위험 | 확정한 요구·설계 revision; 착수 가능한 작업 |
| 테스트 계획서 | 대상 범위, 수준, 환경/데이터, 책임, 진입·종료 조건, 결함 기준 | 요구사항·작업·테스트 케이스 |
| 테스트 케이스/결과서 | 케이스 revision, 절차·기대값 / run의 실제 결과·환경·대상 버전·증빙 | 검증 관계; 과거 실행과 현재 유효성 구분 |

System은 전체 구성과 경계, Infra는 실행 환경, Application은 내부 동작, Interface는 경계를 넘는 계약을 소유한다. 다른 문서의 내용을 복제할 때는 연결된 원본 revision을 표시하고 반복 기술보다 참조를 우선한다. DB 설계·시퀀스 다이어그램은 Application의 하위 산출물, API 명세는 Interface의 하위 산출물로 시작해 필요하면 독립시킨다.

## 참고 원문에서 확장하는 산출물

| 단계 | 원문에 포함된 종류 | 앱에서의 처리 |
|---|---|---|
| 기획·분석 | 사업 기획, 요구사항, 기능 정의, 타당성, WBS, 시장조사, BM, SWOT, 대화 시나리오 | 목적에 따라 선택; 요구·WBS는 구조화 원본에서 문서 보기 생성 |
| 설계 | 시스템, DB, 화면·화면목록·IA, API, 시퀀스, 네트워크 | 네 가지 핵심 설계서와 하위 문서·도식으로 매핑 |
| 개발 | 코딩 표준, 모듈 설계, 설치 가이드, 인터페이스, Git Branch | 개발 가이드·Application·Interface·Infra에 연결 |
| 테스트 | 계획, 케이스, 부하 보고서, QA checklist, 대화 QA | 실행 증빙과 테스트 유형별 선택 템플릿 |
| 배포·운영 | CI/CD, 배포 계획, 릴리즈 노트, 백업/복구, SLA | 운영 범위가 있을 때 추가, 릴리즈와 고정 revision 연결 |
| 보고·관리 | 회의록, 진행 보고, 리스크, 변경 요청 | 결정·위험·변경 객체와 snapshot 보고서 |

참고 문서는 특정 프로젝트의 산출물 안내다. 이를 보편적인 법정 필수 목록이나 ISO 적합성 인증 기준으로 해석하지 않는다. 추가 조사에서 첨부 PDF 2개의 텍스트와 개별 예시를 확인했다. PMM은 ISO 표준 개발 과정의 관리 자료이며 SI 필수 산출물 목록으로 해석하지 않는다. [35종별 실제 확인 상태](10-reference-audit.md)와 [공개 보완 양식](11-template-reference-library.md)을 참고한다.

## 저장·버전·내보내기

문서 본문은 앱 없이 읽고 고칠 수 있는 원본 파일로 보존한다. 스킬 lock·실행·관계는 선택적 sidecar로 관리한다. 산출물 공통 메타데이터는 ID, 유형, 제목, 담당, 상태, revision, 기준 요구사항, 참조 revision, 검토 기록, 출처, 첨부 목록, 생성·수정 시점이다. 내장 문서는 Markdown과 구조화 데이터를 원본으로 저장한다. 업로드 파일은 원본을 변경하지 않고 별도 revision으로 등록한다.

외부 링크는 제목·원본 URL·연결 시점·마지막 확인·접근 상태를 기록한다. 본문을 읽지 않은 링크를 “내용 검증 완료”로 표시하지 않는다. 외부 파일의 변경 탐지와 자동 수집은 연결 권한과 명시한 동기화 정책이 있을 때만 수행한다.

MVP 반출 ZIP은 다음 구조를 제안한다.

```text
project-export/
  manifest.json         schema_version, project_id, baseline, export_time
                        포함 revision, 파일 hash, 외부 링크/누락/비적용
  documents/*.md        문서와 생성형 요구·작업·테스트 보고서
  data/*.json           requirements, tasks, cases, runs, links, decisions
  provenance/*         skills.lock.json, 선택적 run·검수 sidecar
  attachments/*         포함할 권한이 있는 업로드 원본
```

고정한 기준선과 실제로 포함한 내용을 표시한다. 외부 링크의 파일을 가져오지 못했으면 그 사실을 manifest에 남긴다. 렌더링 이미지뿐 아니라 원문·도식 소스·관계를 보존한다. 실행 묶음 반출과 외부 수정 결과 재연결은 MVP 필수다. 기본 파일·sidecar의 hash/diff·충돌 처리를 먼저 제공하고 범용 타 서비스 일괄 migration은 후속 범위로 둔다.

## 양식·예시·스킬의 연결

각 유형은 [참조 registry](references/artifact-templates.json)의 원문 번호·예시 상태·공개 양식·자체 시작 필드·적용 스킬과 연결한다. 스킬 원문은 작성 규칙, 양식은 목차·필드, 예시는 표현 참고, 프로젝트 자료는 사실 근거다. 기존 문서 수정에서는 선택한 양식보다 원본과 보존 범위를 먼저 따른다.
