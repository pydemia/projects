# 아이디어 요건화와 기존 기능 반영

상태: 사용자 필수 요구를 반영한 기능 명세 · v0.2 · 2026-10-21

## 아이디어 작업창

사용자는 프로젝트에 들어가기 전 보관함 또는 프로젝트 내부에서 메모를 작성한다. 자유로운 원문과 후속 대화를 보존하고 출처·적용 프로젝트·관련 기능을 선택한다. 정해진 양식을 모두 채우지 않아도 시작할 수 있다. 메모와 파생 요건은 서로 다른 객체이며 메모를 수정해도 이미 채택한 요건을 몰래 바꾸지 않는다.

작업창은 메모·대화, 요건/기능 연결 제안, 생성할 산출물의 세 영역을 가진다. “요건화”는 `requirements-authoring`을 적용한 LLM 작업이다. “기존 기능 대조”는 해당 스킬에 기존 기능·명세·코드 근거를 함께 전달한다. “구현 반영 계획”은 `development-workflow`로 이어진다. 단계별 `requirements-verification`은 현재 산출물에 필요한 증거만 점검한다.

## 기존 기능의 기준

Feature는 제품의 안정적인 기능 단위다. 기능 ID·현재 동작·화면/API/모듈·요구사항·테스트·근거 revision을 연결한다. 신규 프로젝트는 빈 기능 목록에서 시작한다. 기존 프로젝트는 명세·저장소 자료에서 후보를 추출하거나 수동 등록한다. 문서에만 적힌 기능, 코드에서 관찰한 기능, 실제 실행까지 확인한 기능을 구분한다.

LLM이 기존 동작을 단정하려면 출처와 관찰 범위가 있어야 한다. 필요한 코드를 읽지 못하면 기능 대조 결과를 미검증으로 남긴다. 이름이 비슷하다는 이유만으로 같은 기능이나 중복으로 판정하지 않는다. 자료가 부족해도 메모 작성·요건 초안은 계속할 수 있다.

## 요건 후보별 판단

| 반영 방식 | 판단 내용 | 생성·연결할 결과 |
|---|---|---|
| 신규 기능 | 현재 기능에 없는 동작인가 | 새 Feature 후보 + 새 요건 초안 |
| 기존 기능 확장 | 현재 동작을 유지하며 조건·사용 범위를 추가하는가 | 기존 Feature + 추가 요건 또는 기존 요건의 새 revision |
| 기존 기능 변경 | 기존 기본값·예외·계약이 달라지는가 | 변경 요청 + 영향·호환 검토 + 요건 revision |
| 기존 요건에 통합 | 같은 조건·결과를 이미 요구하는가 | 기존 ID 연결, 추가 설명/수용 조건이 있으면 변경 초안 |
| 중복 | 새 변경이 필요 없는가 | 기존 기능/요건·해당 근거만 연결, 중복 작업 생성 금지 |
| 충돌 | 같은 조건에서 두 요구를 동시에 만족할 수 없는가 | 양쪽 요구·원문·충돌 조건·해결안, 결정 전 반영 보류 |
| 보류/제외 | 현재 범위 밖이거나 결정이 필요한가 | 이유·재검토 조건, 원문 보존 |

한 메모가 여러 요건과 기존 기능으로 나뉠 수 있다. 각 요건에는 주체·조건·기대 동작·예외·수용 조건·출처 문장·기능 관계를 기록한다. 기존 ID는 유지하고 새 요건에만 ID를 발급한다. 제안과 사용자 채택, 계획 반영과 실제 구현 완료를 구분한다.

## 구현 반영 묶음

요건 후보를 검토한 뒤 LLM이 다음 변경안을 한 묶음으로 제시한다.

- 추가·변경·통합할 요건과 Feature 연결
- 기획/UI/System/Infra/Application/Interface 중 바뀌는 문서·섹션과 이유
- 변경할 코드·설정·데이터의 확인된 위치 또는 아직 확인할 위치
- 구현 작업·선행 관계·수용 조건·검증 방법
- 새 테스트와 기존 동작을 보호하는 회귀 테스트
- 미정 질문·호환 위험·롤아웃/복구 검토가 필요한 항목

“반영”은 검토한 요건·문서 변경 초안·작업·테스트 후보를 연결된 상태로 저장한다. 코드 실행·commit·PR·배포를 뜻하지 않는다. 사용자가 이미 허용한 작성·수정 범위에서는 작업을 계속하며, 요구 충돌처럼 결과가 달라지는 미결정만 묻는다. 앱은 단계마다 일률적인 승인 절차를 추가하지 않는다.

적용 시 원안·기능·요건·문서 revision을 다시 비교하고 바뀌었으면 재검토한다. 동일 proposal 적용은 멱등하게 처리해 요건과 작업을 중복 생성하지 않는다. 적용 전 취소는 원본을 유지한다. 적용 후 되돌리기는 파생 기록의 폐기/되돌림 revision을 남기고 공유 이력을 삭제하지 않는다.

## 예시

메모: “문서의 이전 버전과 현재 버전을 나란히 비교하고, 필요한 내용만 새 초안으로 복원하고 싶다.”

기존 기능 `FEAT-02 문서 버전 관리`에는 확정본 보존·전체 복원이 정의되어 있다고 가정한다. 확인한 명세 revision과 코드 위치가 있을 때만 이 상태를 관찰 사실로 표시한다. LLM은 비교 화면·부분 복원이라는 추가 동작을 추출해 “기존 기능 확장”을 제안한다.

사용자가 채택하면 기존 `REQ-002`와 연결한 새 요건 초안, UI 비교 화면 설계 수정, Application의 복원 규칙 보완, 비교·부분 복원 구현 작업, 확정본 불변·부분 선택·취소·동시 수정 회귀 테스트 후보를 생성한다. 구현 후 실제 코드와 실행 결과가 연결되어야 반영 완료로 판정한다.

이 예시는 기획 시연용이며 실제 제품의 구현 상태를 보고한 내용이 아니다.
