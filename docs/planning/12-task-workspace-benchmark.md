# 개인·프로젝트 작업공간 벤치마크와 기능 기획

2026-10-21 · 근거: 아래 제품의 공식 도움말과 Projects 현행 구현

## 비교에서 채택한 행동

| 제품·근거 | 관찰한 패턴 | Projects에 적용하는 판단 |
|---|---|---|
| [ClickUp Views](https://help.clickup.com/hc/en-us/articles/6310383076503-Task-views), [Dashboard](https://help.clickup.com/hc/en-us/articles/16956329804311-Use-time-based-Dashboard-cards) | 같은 작업을 List·Board·Calendar·Timeline·Workload 등으로 보고, 대시보드에서 분포·추세를 살핀다 | 하나의 작업 ID/상태를 목록·보드·캘린더·집계로 재표현한다. 첫 집계는 현재 상태의 분포이며 시계열·작업량 계획은 별도 이력 설계 후 확장한다 |
| [Jira 필터](https://support.atlassian.com/jira-software-cloud/docs/filter-work-items/) | 목록·보드·캘린더·타임라인에서 작업 필터를 사용한다 | 보기 전환은 작업 자체를 복제하지 않는다. 검색·상태·우선순위 기준을 보기와 독립적으로 둔다 |
| [Confluence 연결](https://support.atlassian.com/confluence-cloud/docs/database-fields/) | 구조화된 데이터와 문서·Jira 작업을 링크로 연결한다 | Projects는 작업·근거 관계를 소유하고 문서 본체는 Note 이관 계약을 유지한다. 문서를 작업 관리 기능에 재구현하지 않는다 |
| [Microsoft To Do My Day](https://support.microsoft.com/en-US/ToDo/my-day-and-suggestions) | 오늘에 집중하는 스마트 목록과 간단한 작업 입력 | 간편 보기의 오늘·Inbox·예정을 제공한다. 오늘 목록은 실행 예정일과 지난 마감으로 계산하며 사용자의 작업을 밤에 자동 이동·삭제하지 않는다 |
| [TickTick 목록](https://help.ticktick.com/articles/7055782283059396608), [캘린더·집중](https://help.ticktick.com/) | Inbox·Today·Next 7 Days, 달력과 집중 도구 | Inbox·예정·월간 달력과 예상 소요를 우선 적용한다. 알림·반복·타이머는 데이터/알림 계약을 정한 후 추가한다 |
| [Todoist 필터](https://www.todoist.com/help/todoist/features/use-the-board-layout-in-todoist-AiAVsyEI) | 같은 작업을 목록·보드로 바꾸고 날짜·우선순위 등을 표시 | 간단 검색과 작업 메타데이터를 제공한다. 필터 DSL·하위 작업 조작은 이번 범위에 포함하지 않는다 |

이 비교는 타 제품의 UI 모양을 복제하기 위한 것이 아니다. Projects의
아이디어→요구→설계·작업→테스트 추적을 보존하면서 개인 할 일에도 같은
작업공간을 쓰기 위한 행동 기준이다.

## 두 작업 방식의 공존

[GTD의 실행 시 선택 기준](https://gettingthingsdone.com/2010/06/you-are-in-control-when-you-can-see-it-all/)은
맥락·가용 시간·에너지·우선순위다. Projects는 `다음 행동`, 실행 맥락,
예상 소요 분, 필요 에너지를 따로 저장하고 사용자가 입력한 현재 조건에
맞는 작업을 먼저 보여 준다. 예상 소요를 기록하지 않은 작업은 숨기지 않고
뒤에 남긴다.

[Franklin Planner의 ABC123](https://www.franklinplanner.com/certifications/planner.html)은
목표·가치에 근거한 A/B/C와 각 그룹의 실행 순서다. Projects는 ABC 등급,
그룹 내 순서, 연결 목표·가치를 저장한다. 실행 순간의 GTD 조건과 전략적
ABC 등급은 서로 다른 축이다. GTD 보기에서 A를 자동 변경하거나, ABC
보기에서 소요 시간을 중요도로 바꾸지 않는다. 사용자가 정렬 기준을 전환한다.

## 업무 개념과 화면

작업 유형은 `개인 할 일`과 `구현 작업`이다. 개인 할 일은 제목만으로 만들고
완료할 수 있다. 구현 작업은 기존의 수용 조건·결과 URL·선행 작업·필요한
테스트와 같은 commit SHA의 통과 근거를 유지한다. 작업 유형을 생성 후
전환하지 않아 엄격한 완료 검사를 화면 전환으로 우회할 수 없다.

`간편 · To-do`와 `정교 · 프로젝트`는 작업 데이터·프로젝트 프로필·시각
UI 모드와 별개인 **보기 밀도**다. 간편 보기는 오늘·Inbox·예정과 빠른 입력,
개인 할 일 완료를 중심에 둔다. 정교 보기는 목록·보드·캘린더·집계와
상태·일정·GTD·ABC·GitHub Issue·근거 편집을 드러낸다. 전환해도 항목 ID,
revision, 저장 내용은 바뀌지 않으며 URL의 `taskMode`, `taskView`, `item`을
통해 현재 보기를 재방문할 수 있다. 간편 보기의 상세 설정 행동은 정교
보기에서 같은 항목을 연다.

| 보기 | 기본 질문 | 핵심 조작·빈 상태 |
|---|---|---|
| 오늘 | 오늘 무엇을 처리할까? | 실행 예정일이 오늘이거나 마감이 지난 열린 작업. 한 줄 추가와 개인 할 일 완료. 해당 작업이 없으면 다른 보기·새 작업 안내 |
| Inbox | 분류 전 무엇이 남았나? | `Inbox` 목록의 열린 작업. 오늘과 겹쳐도 같은 항목이며 복제하지 않음 |
| 예정 | 다음에 무엇이 오나? | 미래 실행 예정일 또는 실행일 미지정의 미래 마감. 날짜 없는 작업은 Inbox·목록에서 확인 |
| 목록 | 어떤 상태·목록·우선순위인가? | 검색·상태·GTD/ABC 정렬. 항목 상세·revision 편집 |
| 보드 | 상태별 병목은 어디인가? | 같은 작업을 상태 열에 표시. 이번 단계는 열에서 상세 열기, 드래그 상태 변경은 후속 |
| 캘린더 | 예정일·마감일이 언제인가? | 월간 날짜 셀에 두 날짜를 표시. 날짜 미지정은 목록에 남음 |
| 집계 | 현재 분포는 어떤가? | 현재 검색·상태 조건에 맞는 작업의 상태·지난 마감·ABC별 건수와 진행 중 예상 시간. 이력 기반 추세로 오인하지 않도록 `현재 스냅샷` 표기 |

GitHub 연결의 첫 단계는 정규화된 `https://github.com/{owner}/{repo}/issues/{number}`
URL을 작업에 저장·열람하는 것이다. 이 URL은 Projects 작업의 완료 근거나
GitHub 상태의 자동 동기화로 간주하지 않는다. 인증·권한 철회·비공개 Issue,
중복/역순 webhook, 충돌·소유권을 정의한 후 읽기 동기화와 양방향 동작을
단계적으로 추가한다. 이는 기존 APP-REQ-001의 GitHub 후속 계약을 구체화한다.

## 수용 기준과 다음 확장

1. 간편/정교 전환과 보기 이동 후 같은 작업 ID·revision·완료 상태를 보여 준다.
2. 개인 할 일은 제목만으로 저장·완료·다시 열기가 가능하며, 구현 작업의
   기존 완료 gate는 유지된다. 409 충돌 시 기존 초안·서버 데이터를 지우지 않는다.
3. GTD 조건과 ABC 등급은 독립적으로 수정·정렬되며 미산정 작업은 사라지지 않는다.
4. 예정/마감·상태·ABC 그래프의 값은 같은 저장된 작업 목록과 일치한다.
   시계열로 표시하지 않는다.
5. 잘못된 날짜·음수 소요·외부 호스트 Issue URL은 저장 거부한다. Issue 링크를
   눌러도 API 인증 정보는 전달하지 않는다.
6. 좁은 화면·키보드·light/dark·다른 출시 UI 모드에서 작업이 읽히고 조작된다.

후속 범위는 반복 작업·알림, 소요 시간 실측/집중 타이머, 하위 작업과
다중 선택·일괄 편집, 저장된 고급 필터, 드래그 보드, Gantt·작업량·이력
그래프, 전 프로젝트 개인 Today, GitHub Issue 읽기/양방향 동기화다. 각
항목은 소유권·동기화·일정 시간대·이력 자료 계약을 정한 뒤 구현한다.
