이 문서는 [기존 작업공간 기획](12-task-workspace-benchmark.md)의 화면 비교를 실제 조작 기준으로 보완한다. 사용자가 보드를 보고 일을 움직이고, 수정하고, 다시 열었을 때 결과를 믿을 수 있어야 한다. 이번 요청으로 **보드 카드 드래그 이동과 순서 변경은 최우선 필수 개선**으로 승격한다. 나머지 확장은 아래에서 필수와 제안을 구분한다. Note 문서 본문, Hub 스킬 원문, GitHub Issue 연동 소유권은 기존 계약을 유지한다.

## 분석 당시 UX의 결손

1. 보드 카드에 드래그 핸들·드롭 대상·위치 미리보기·키보드 이동 경로가 없다. 상태 선택창 외에는 배치 행동이 없다. 카드의 `NativeSelect`는 현재 값·후보만 열어 이동/편집/복제 같은 작업 행동을 찾을 메뉴가 없다.
2. 서버 모델에 **수동 순서**가 없고 현재 `visible`은 GTD/ABC 기준으로 매번 정렬된다. 화면에서만 카드 순서를 바꾸면 재접속 때 되돌아간다.
3. 보드 열 안에서 작업을 만들 수 없으며, 빠른 입력이 현재 열·위치를 상속하지 않는다. 여러 작업 선택·일괄 상태 변경도 없다.
4. 일정 화면은 월간 표시 중심이며 날짜 없는 작업을 끌어 배정하거나 일정 변경을 조작할 수 없다. 집계는 현재 스냅샷만 있어 변경량·처리 시간 추세는 알 수 없다.
5. 기존 테스트는 카드 표시와 상태 `<select>` 변경을 확인하지만 실제 포인터 이동·순서 지속성·실패 복구·모바일 대체 조작은 확인하지 않는다.

## 개선 범위와 사용자 흐름

### P0 · 작업 가능한 상태 보드 (이번 요청의 필수 개선)

- 정교 모드의 상태 보드 기본 정렬은 `수동 순서`다. 카드 드래그로 **열 사이 상태 이동**과 **같은 열 안 순서 변경**을 한다. 놓을 위치 표시, 빈 열 드롭 영역, 긴 열 자동 스크롤, 이동 중 카드·대상 열의 구별, 저장 중·완료·실패 피드백을 제공한다.
- 드래그는 카드 본문 클릭·인라인 버튼·텍스트 선택과 충돌하지 않게 핸들/활성 거리로 시작한다. 터치에서 끌기 어렵거나 키보드를 쓰는 사람은 카드 메뉴의 `상태로 이동`과 `위로/아래로 이동`으로 **동일한 서버 동작**을 수행한다.
- 카드의 상태 배지와 `…`는 **서로 다른 컨트롤**이다. 상태 배지는 현재 상태·가능한 전이·검색/선택을 보여 주는 상태 메뉴를 열고, `…`는 이동·편집 등 작업 행동 메뉴를 연다. 메뉴의 `상태로 이동`/`위로·아래로`와 드롭은 같은 서버 명령·완료 gate·오류 복구를 공유한다. `다른 목록으로 이동`은 상태 열 이동과 별도 명령이며 현재 프로젝트/목록과 대상 위치를 명시한다.
- 간편 모드에서는 완료, 오늘로 계획, 상태 이동, 편집을 한 단계 이내에 두고 나머지는 `…` 안에 접는다. 정교 모드에서는 상태·ABC/GTD·날짜 등 자주 바꾸는 필드를 카드에서 열되, 정보량이 많아도 카드 제목·드래그 핸들·`…`를 가리지 않는다. 메뉴는 복잡한 서비스의 전체 항목을 복제하지 않고 Projects에서 실제 제공하는 행동만 노출한다.
- 상태 이동과 수동 순서를 PostgreSQL에 저장한다. 새로고침·보기 전환·다른 세션에서 같은 순서가 보인다. GTD/ABC 값은 이동으로 자동 변경되지 않는다. 자동 정렬을 켜면 상태 간 이동은 허용하되 열 안 수동 재정렬은 비활성화하고 이유를 표시한다.
- 완료 열로 옮긴 `personal` 작업은 기존 간단 완료 계약을 따른다. `delivery` 작업은 근거·테스트 gate를 통과할 때만 완료된다. 미충족 시 원위치와 입력을 유지하고 필요한 상세 항목으로 안내한다.
- 권한 없음·무효 대상·409 충돌·네트워크 실패에서는 화면만 성공한 듯 남기지 않는다. 낙관적 이동을 되돌리고 사유·재시도/새로고침을 제공한다. 성공 직후 되돌리기는 변경 충돌을 검사한다.
- 필터로 숨겨진 작업은 삭제·재정렬되지 않는다. 보이는 이웃 카드 기준으로 서버에 위치를 요청하고 숨은 작업의 상대 순서는 유지한다. 빈 열/마지막 위치도 유효한 대상이다.

### P1 · 일상 작업을 줄이는 제안

- 열별 빠른 생성: 제목만 입력해 해당 상태와 기본 위치로 저장한다. 간편 모드의 빠른 수집은 기존 Inbox/오늘 기본값을 유지한다. 제목 편집·일정·ABC/GTD 필드는 카드 또는 상세에서 바로 열고 저장 실패를 표시한다.
- 다중 선택/일괄 행동: 선택 수와 대상 목록을 명시한 도구막대에서 상태·실행 예정일·목록 이동을 처리한다. 불가능한 `delivery` 완료가 섞이면 전체 적용 전에 대상별 차단 사유를 보여 주며 무심코 일부만 완료하지 않는다. 모바일에서는 메뉴로 같은 행동을 제공한다.
- `오늘 계획`과 연기: Inbox/목록의 작업을 오늘에 추가·제외하고, 완료하지 못한 작업은 내일/날짜 선택으로 명시적으로 연기한다. `planned_date`와 `due_date`는 분리한다. GTD의 실행 조건과 ABC의 가치 등급은 계속 독립이다.
- 저장된 보기: 프로젝트별 기본값/개인 보기로 그룹·필터·정렬·카드 표시 필드를 기억한다. 보기 설정과 작업 데이터 변경을 구분해 저장한다. 다른 사람의 보기 설정을 조용히 바꾸지 않는다.
- 개인 칸반 섹션: TickTick의 섹션은 `state`와 다른 분류다. 실제 수요와 목록/섹션 구조를 결정한 뒤 별도 속성으로 도입한다. 현행 `list_name`을 상태나 섹션으로 암묵 변환하지 않는다.

### P2 · 근거가 쌓여야 가능한 제안

- 일정의 날짜 없는 작업 트레이, 달력 끌기/늘리기와 주·일 보기, 반복·알림/집중 시간은 시간대·반복 인스턴스·알림 계약을 정한 뒤 구현한다.
- 집계의 생성/완료 추세·리드타임·상태 체류시간은 작업 변경 이벤트가 저장된 **이후 구간**만 계산한다. 현행 `현재 스냅샷` 막대를 역사 그래프로 다시 이름 붙이지 않는다.
- GitHub Issue 상태 읽기/양방향 이동은 인증·권한·webhook·충돌 계약을 별도로 거친다. 보드 드래그가 외부 Issue 상태를 자동 변경하지 않는다.

| 같은 열 안 드롭 | `state` 그대로, 수동 순서만 갱신 | GTD·ABC·마감 값 불변; 재접속 후 동일 |
| 자동 정렬 선택 | 해당 보기의 표시 순서만 GTD/ABC로 계산 | 수동 순서 값 보존; 열 안 드롭 비활성화 이유 표시 |
| 다중 이동 | 선택한 ID·개별 기대 revision과 대상 위치를 한 요청으로 전달 | 전체 검사 후 원자적 적용 또는 전체 거부; 중복·타 프로젝트 ID 거부 |
| 카드 상태 메뉴/작업 메뉴 | 상태 전이는 보드 드롭과 같은 `move/reorder` 계약, 목록 이동은 별도 명령 | 현재 값·선택 결과·미지원/권한 없는 행동을 구별. 보관/삭제는 메뉴에 노출하더라도 별도 확인·복구 계약 없이는 실행하지 않음 |
| 캘린더 날짜 이동 | 기본적으로 `planned_date`만 변경 | `due_date` 변경은 명시적으로 선택; 시간대와 날짜 경계 검증 |

수동 순서는 `abc_order` 또는 `priority`를 재사용하지 않는다. 저장소 설계에서는 작업별 rank를 PostgreSQL에서 관리하고 같은 프로젝트/상태의 이웃 ID를 기준으로 서버가 위치를 결정한다. 기존 항목은 생성 시각·ID 기준으로 결정적 초기 순서를 부여한다. 정확한 인덱스/랭크 형식은 구현 단계에서 검증하되 **동시 이동, 중복 요청, 권한, 완료 gate, rank 충돌 복구**가 가능해야 한다. 변경 이력은 상태 전이와 사용자에게 의미 있는 일정 변경부터 남기고, 과거 데이터는 이력이 없다고 표기한다.

공통 `ui.pydemia.ai`의 Card·Tabs·Badge·Dialog·메뉴·상태 토큰을 사용한다. 분석 당시 [편입 기록](../implementation/ui-component-integration.md)에 정렬/드래그 primitive가 없었으므로 원본 registry의 제공 여부를 확인 대상으로 삼았다. 후속 구현에서 같은 고정 revision의 Kanban·Popover·DropdownMenu를 편입했다. Projects 전용 카드 모양만 따로 만들지 않는다. simple/complex, 21개 UI 모드, light/dark에서 정보·드롭 위치·선택·오류의 의미가 유지되어야 한다.

## 수용 조건과 검증 경로

| ID | 실제 사용으로 판정할 조건 | 검증 |
|---|---|---|
| AC-40 | A를 할 일 열에서 진행 열로 드래그하면 상태와 열 건수가 바뀌고 새로고침/목록 전환 뒤에도 유지 | PostgreSQL 통합 + 실제 브라우저 포인터 E2E |
| AC-41 | 같은 열에서 A/B 순서를 바꾸면 다시 접속해도 순서가 유지된다. GTD/ABC 정렬을 켜면 수동 순서가 보존되고 조작 가능 여부가 설명된다 | 순서·필터 경계 통합 + 브라우저 E2E |
| AC-42 | 빈 열·긴 열·필터 상태에서도 유효한 대상이 보이고, 무효 드롭/취소는 저장 변경이 없다 | 브라우저 포인터/터치 폭, DB 상태 대조 |
| AC-43 | 근거 없는 구현 작업을 완료 열로 놓으면 완료되지 않고 상세 근거 안내가 열린다. 개인 작업은 허용된다 | 기존 완료 gate와 같은 PostgreSQL 통합 + 브라우저 |
| AC-44 | 409·권한 거부·네트워크 실패 때 카드/카운트가 서버값으로 복귀하고 사용자가 이유와 재시도 경로를 볼 수 있다 | API 실패 주입 + 브라우저 |
| AC-45 | 키보드·터치 사용자가 메뉴로 상태/순서를 바꿀 수 있고 포커스·스크린리더 안내가 유지된다 | 수동 접근성 + 브라우저 E2E |
| AC-46 | 열별 생성이 상태를 상속하며 목록·보드·캘린더/집계가 같은 ID를 보인다 | PostgreSQL 통합 + 브라우저, P1 적용 시 |
| AC-47 | 다중 선택/일괄 이동은 전체 성공 또는 전체 실패하고 선택·충돌 정보를 유지한다 | PostgreSQL 통합 + 브라우저, P1 적용 시 |
| AC-48 | 오늘 계획/연기는 마감일을 임의로 바꾸지 않고, 저장된 보기는 작업 내용과 구분된다 | 통합 + 브라우저, P1 적용 시 |
| AC-49 | 추세 그래프에는 실제 이벤트가 존재하는 기간·분모·미기록 기간을 표시한다 | 이벤트/집계 테스트, P2 적용 시 |
| AC-50 | 상태 배지는 현재 값을 가진 검색 가능한 메뉴를 열고, `…`는 실제 제공하는 작업 행동을 연다. 상태 메뉴/이동 메뉴/드래그가 같은 저장·완료 gate·오류 복구를 거친다 | 브라우저 포인터·키보드 E2E + PostgreSQL 통합, P0 |
| AC-51 | 카드 클릭·드래그·메뉴 열기가 서로 간섭하지 않는다. 메뉴는 화면 경계에서 잘리지 않고 Escape/바깥 클릭으로 닫히며 초점이 원래 카드로 돌아간다. 좁은 화면에도 같은 핵심 행동이 있다 | 넓은/좁은 화면 브라우저 및 접근성 검사, P0 |

시각 스냅샷이나 DOM 존재 검사만으로 AC-40~51을 통과시키지 않는다. 특히 실제 포인터 드래그, 메뉴를 통한 같은 이동, 저장 요청, PostgreSQL 재조회, 새로고침 뒤 순서를 한 시나리오로 검증한다. mock·개발·운영 브라우저 결과를 [검증 기록](../implementation/verification.md)에 별도 표기한다. 구현 순서와 서버 계약은 [상호작용 구현 계획](../implementation/task-interaction-plan.md)에 있다.
