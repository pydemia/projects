# Projects 모바일 UI·UX 기획

2026-10-22 · 상태: **기획 기준선 · 로컬 앱 구현/브라우저 검증 진행** · 범위: 개인 중심 Projects의 웹 모바일 화면

## 결정과 근거

모바일의 기본 과업은 **선택한 프로젝트에서 오늘 할 일을 확인하고, 한 줄로 수집하고, 상태·실행 예정일을 바꾸는 것**이다. 데스크톱의 정보 밀도와 여러 창을 1열로 쌓지 않는다. 같은 PostgreSQL 작업 ID·revision·관계와 URL을 유지하면서 탐색, 표시 밀도, 조작 표면을 기기 폭에 맞게 바꾼다. `간편/정교`는 업무 보기 밀도이고 `ui.pydemia.ai`의 UI 모드·light/dark는 외형 설정이다. 두 축을 모바일 여부와 혼동하지 않는다.

기존 [390px 개요 캡처](../implementation/screenshots/overview-mobile.png)와 [문서 캡처](../implementation/screenshots/documents-mobile.png)는 실제 로컬 브라우저 검사에서 얻은 **이전 화면**이다. 현재 저장소의 `workspace-refresh.css`는 760px 이하에서 사이드바를 세로로 쌓고 메뉴를 가로 스크롤로 바꾼다. `App.tsx`는 프로젝트 선택과 테마·ZIP·로그아웃을 본문 앞에 둔다. `task-workspace.css`는 필터와 일괄 도구막대를 줄바꿈하고 달력에 `min-width: 700px`을 유지한다. 따라서 페이지 가로 넘침 검사 통과와 별개로 첫 과업이 화면 아래로 밀리고, 보드·달력의 조작 단위가 휴대전화 폭에 맞지 않는다. 사용자가 실제 모바일에서 화면 깨짐을 보고했다. 이번에는 실제 물리 기기의 터치·키보드·안전 영역을 재현하지 않았으므로 특정 OS별 결함은 구현 검증 대상으로 남긴다.

참조는 모바일에서 **어떤 조작을 언제 드러내는지**에 한정한다. [ClickUp 모바일 Home](https://help.clickup.com/hc/en-us/articles/15146214337559-Intro-to-Home-on-mobile)은 Today 진입과 상태/일정 행동을, [모바일 Board](https://help.clickup.com/hc/en-us/articles/7255343771287-Use-Board-view-on-mobile)는 보기 전환·필터 조작을 분리한다. [Todoist 모바일 보드](https://www.todoist.com/help/todoist/features/use-the-board-layout-in-todoist-AiAVsyEI)는 현재 구획에서 빠른 생성과 목록/보드 전환을 보여 준다. [모바일 탐색 가이드](https://developer.android.com/design/ui/mobile/guides/layout-and-content/layout-and-nav-patterns)는 적은 수의 상위 목적지에 하단 탐색, 나머지에 drawer/menu를 권한다. 이는 Projects의 **설계 참고**이며 이들 앱의 모바일 UI가 Projects에서 검증되었다는 뜻은 아니다.

## 화면 구조

| 관계·과업 | 넓은 화면의 현행/유지 | 모바일 설계 |
|---|---|---|
| 전역 탐색 | 프로젝트 사이드바와 7개 업무 메뉴 | 짧은 상단 바에 현재 프로젝트 이름·전환 버튼. 프로젝트가 있으면 맨 위 항목을 자동 선택하고, 전환 버튼은 세로 행 목록 시트를 연다. 시트에서 위·아래 이동 버튼으로 순서를 바꾸며, 전체 목록에서는 드래그도 사용한다. 프로젝트가 없으면 만들기 화면을 보인다. 하단 4개 목적지 `오늘`·`Inbox`·`작업`·`더보기`를 둔다. `더보기`에서 개요·기획·임시 문서·테스트·추적·스킬 작업 및 계정/테마/반출을 연다. `오늘`·`Inbox`는 **현재 프로젝트 범위**라고 상단에 명시한다. 전 프로젝트 통합 Today로 오인시키지 않는다. |
| 작업 수집 | 본문 상단의 제목·날짜 폼 | 한 개의 `+ 추가` 행동이 제목 입력 sheet를 연다. 현재 Today/Inbox/보드 열의 기본 실행 날짜·상태를 미리 표시하고 수정할 수 있다. 저장 실패 시 제목·선택값을 유지한다. 키보드가 열리면 하단 탐색과 충돌하지 않는다. |
| 작업 탐색 | 간편/정교 전환, 현황 카드, 보기 탭, 다수 필터 | 첫 화면은 현재 보기 이름·건수, 검색·필터 버튼, 작업 목록 순서다. `간편/정교`와 현재 개인 저장 보기는 보기 메뉴에서 확인·전환한다. 목록/보드는 `작업`의 우선 선택지로, 캘린더·집계는 같은 보기 메뉴의 추가 선택지로 둔다. 필터 개수와 활성 저장 보기 이름은 접힌 상태에서도 보인다. |
| 정보 세부 | 목록/상세 동시 표시 또는 상세가 목록 아래 | 한 번에 한 영역. 목록의 행을 열면 동일 `item` URL의 전체 화면 상세로 이동한다. 뒤로 가면 이전 검색·보기·스크롤과 선택 상태를 복원한다. |
| 다중 행동 | 체크박스·Shift와 여러 필드 도구막대 | `선택`을 누르면 행 체크박스와 하단 `n개 선택` 행동 막대가 나타난다. 상태·실행 예정일·목록은 각 sheet에서 목표·영향을 확인한 뒤 적용한다. 기존 원자적 API와 완료 gate를 그대로 사용한다. 필터 때문에 보이지 않는 선택이 있으면 수를 밝혀 사용자가 적용 범위를 알게 한다. |

하단 탐색과 `+ 추가`는 엄지로 닿는 영역에 두되, 사용자가 입력·상세·선택 sheet를 열면 해당 과업에 필요한 저장/취소만 남긴다. 상단 바에는 화면 제목과 현재 프로젝트를 남기고 브랜드·소개 문구·현황 카드 반복은 본문 첫 화면에서 줄인다. `더보기`는 단순한 숨김 창이 아니라 모든 기존 업무 화면에 도달하는 안정적인 경로여야 한다. 데스크톱 사이드바는 유지하고 중간 폭은 콘텐츠와 입력 방식에 따라 1~2 pane/rail로 전환한다. 정확한 CSS 경계는 구현 단계의 콘텐츠 측정으로 정한다.

## 과업별 모바일 화면

### 오늘·Inbox·빠른 수집

오늘은 `오늘 n개`와 열린 작업을 바로 보여 준다. 마감 지남, 오늘 실행 예정, 그 밖의 오늘 마감을 텍스트 표식으로 구분한다. 행에는 완료/상세, 제목, 실행·마감 중 중요한 날짜와 ABC/GTD 단서 한 줄을 우선 둔다. `오늘로`, `내일로 연기`, 상태 변경은 행 메뉴 또는 상세의 큰 행동에서 제공한다. 연기는 `planned_date`만 바꾸며 `due_date`가 지난 항목은 오늘에도 남는 이유를 보여 준다. 구현 작업의 완료는 근거 gate를 우회하지 않고 필요한 상세로 안내한다. Inbox는 날짜가 없는 수집 목록과 `오늘로`를 우선한다. 간편 화면에서 고급 정렬·맥락·에너지는 `필터` sheet에 둔다.

### 정교 목록·보드·캘린더·집계

정교 목록은 검색·활성 필터·저장 보기 이름을 고정된 짧은 도구 줄에 보이고, 그룹 제목 아래에서 제목과 핵심 메타데이터만 반복한다. `선택` 중에는 완료 체크와 일괄 선택을 시각·접근 가능한 이름으로 구분한다. 보드는 **현재 상태 열 한 개를 온전히 읽는 화면**으로 바꾼다. 상태 이름·건수 선택기로 다섯 열에 곧바로 이동하고, 옆 열은 스와이프/스크롤로 이동할 수 있되 상태 선택기가 항상 대체 경로다. 열 아래 빠른 생성은 현재 상태와 맨 뒤 순서를 상속한다. 카드 본문은 상세, `…`는 상태/위아래 이동 메뉴이며 터치 드래그만을 유일한 경로로 삼지 않는다. 기존 서버의 revision·완료 gate·숨은 카드 순서 보존을 공유한다. 수동/자동 정렬 가능 여부도 보드에서 보인다.

캘린더는 7열×여러 주의 축소판 대신 **주간 날짜 띠 + 선택일의 세로 agenda**를 기본으로 한다. 날짜 셀에는 건수, 선택일에는 작업 제목과 `실행 예정`/`마감`을 별도 표식으로 보인다. 월 선택과 날짜 없는 작업 목록으로 이동할 수 있다. 날짜 드래그 변경은 P2 계약 전에는 만들지 않는다. 집계는 현재 스냅샷의 총계와 막대를 한 열로 쌓고, 분모·필터·이력 없음 설명을 유지한다. 작은 화면을 이유로 시계열 그래프를 만들어 보이게 하지 않는다.

### 기획·문서·테스트·추적·스킬 작업

`더보기`의 각 업무 영역은 **목록 → 항목 전체 화면 → 편집/관계/근거 탭**으로 전환한다. 아이디어 메모·요건화의 원문과 선택 반영 결과는 별도 단락이며, 결과를 자동 적용으로 오인시키지 않는다. 임시 문서는 Markdown 원문 편집과 미리보기를 탭으로 전환하고, 미저장 초안·409 비교·저장 행동을 입력 키보드 위에 유지한다. 본문이 길어도 기존 Note 이관 경계를 유지한다. 테스트 케이스·실행 결과는 요약 행과 상세에서 단계·예상·실제 결과를 읽는다. 추적 표는 좁은 화면에서 관계별 행(`요건 → 설계/작업/테스트`)으로 재구성하고 원래 링크·revision·판정 근거를 보존한다. 스킬 작업은 입력·실행 상태·제안·명시 적용을 단계별로 표시하며 초안 검토 없이 적용하지 않는다.

## 상호작용과 상태 계약

- **보기 전환:** `project`, `view`, `taskMode`, `taskView`, `savedView`, `item` URL을 데스크톱과 공유한다. 창 크기가 바뀌어도 항목 ID·저장된 보기·서버 데이터는 그대로다. 모바일 전용 pane/열 위치·필터 sheet 열림 여부·목록 스크롤은 화면 상태로 유지한다. 기본 개인 보기를 다른 사람에게 적용하지 않는다.
- **초안과 실패:** 입력 중 화면·보기 전환 시 제목/본문 초안을 보존하거나 명시적인 이탈 선택을 제공한다. 서버 응답 전에는 완료된 것처럼 표시하지 않는다. 409/권한/네트워크 실패 시 대상과 이유, 재시도·최신 자료 확인 경로를 보여 주고 다중 선택·입력값을 보존한다.
- **기본 제스처와 대체 행동:** 보드 스와이프는 열 탐색, 카드의 명시적 메뉴는 상태·순서 변경이다. 스와이프·장시간 누르기·드래그가 없어도 동일 행동에 도달해야 한다. 실수로 손가락이 움직여 카드 상세가 열리거나 상태가 바뀌지 않게 시작 범위를 구분한다.
- **레이어와 포커스:** 메뉴·필터·추가·일괄 변경은 현재 화면 위 한 개의 sheet/dialog만 연다. 닫기/취소/뒤로/Escape의 의미와 원래 버튼으로의 포커스 복귀를 일치시킨다. 브라우저/OS 뒤로는 상세→목록, sheet→기존 화면 순으로 동작한다.
- **가독성·접근성:** 터치 주요 버튼은 44~48 CSS px을 설계 목표로 하고, 작은 보조 컨트롤도 [WCAG 2.2 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)의 24px 또는 충분한 간격 기준을 검증한다. 320 CSS px에서 본문과 주요 조작의 두 방향 스크롤을 피한다([WCAG 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)). 표/보드처럼 공간 구조가 필요한 곳은 **영역 내부** 스크롤과 명시적 대체 보기·조작을 제공한다. 브라우저 확대, 긴 한국어·영어 URL, 키보드 표시, 하단 안전 영역, 가로 방향, 축소된 동작 설정을 검증한다.

### 2026-10-25 모달 사용성 보완

짧은 작업 입력·필터·더보기는 하단 시트로 유지하고, 프로젝트 생성·Git 소스
가져오기·아이디어/문서 등 긴 폼은 모바일 전체 화면 dialog로 연다. 전체 화면
dialog는 제목·닫기를 상단에 고정하고 본문만 스크롤한다. 한 개 폼의 저장/취소
행은 화면 하단에 두며 긴 폼에서도 스크롤 중 접근할 수 있게 한다. 시트의
`추가`·`결과 보기` 버튼도 작은 가시 영역에서 접근 가능해야 한다.

위치는 레이아웃 viewport가 아닌 `visualViewport`의 현재 상단·폭·높이·하단을
사용한다. OS 키보드·확대·스크롤로 보이는 영역이 바뀌면 열린 dialog를
재배치하고, 안전 영역을 본문 하단 여백에 반영한다. 닫기·Escape 이후에는
열었던 버튼으로 초점을 돌린다. 320×568·390×844·667×375 및 키보드로
가시 높이가 300/200 CSS px로 줄어드는 상태에서 제목·닫기·주요 행동이
가려지지 않아야 한다. 실제 iOS/Android OS 키보드·안전 영역은 물리 기기에서
후속 확인한다.

## 표현과 공통 UI 인계

기존 pydemia identity, Glassmorphism 기본값, 21개 UI 모드와 light/dark/System, 승인 favicon을 유지한다. 같은 역할의 작업 행은 같은 여백·구분선·타이포를 쓴다. 상태·마감 지남·선택은 글자와 아이콘/배지로도 구별한다. 개별 행은 필요할 때만 경계를 갖고, 한 업무 영역 전체의 면·행마다의 테두리·다시 내부 카드 테두리를 반복하지 않는다. sheet는 주변 화면과 겹치는 독립 영역이므로 명확한 표면·포커스 경계를 가진다. 기존 활성 탐색 행은 면·굵기·`aria-current`로 표시하고 장식용 왼쪽 강조 줄을 추가하지 않는다.

| 과업/화면 | 이미 편입해 확인한 `ui.pydemia.ai` source | 모바일 조정·공백 |
|---|---|---|
| 외곽·탐색 | `AppShell`, `AppSidebar`, `Navigation`, `Button`, `NativeSelect`, `ThemeScope` | 상단 프로젝트 선택·하단 4목적지·`더보기` drawer는 기존 source 조합으로 설계. 모바일 전용 navigation/drawer item은 구현 전에 registry의 실제 variant·출처·접근성 상태 확인 |
| 오늘·목록·선택 | `Tabs`, `SearchInput`, `Checkbox`, `Badge`, `Field`, `DropdownMenu`, `Card` | 행의 완료/선택을 명확히 분리하고 메타데이터를 우선순위로 접는다. 현재 저장된 보기·필터 수를 노출 |
| 추가·필터·상세 | `Dialog`, `Input`, `Textarea`, `Accordion`, `Popover`, `Field` | 기존 Dialog를 모바일 sheet로 배치 가능한지 source/포커스/portal 검사. `Sheet` source가 없다면 기존 Dialog의 반응형 표현을 조정하며 새 primitive를 검증 없이 도입하지 않음 |
| 보드·집계·추적 | `Kanban`, `BarList`, `Table`, `DataList` | Kanban은 한 열 보기와 동일 이동 API, BarList는 1열, Table은 관계 행 대체와 원본 표 접근 경로를 둠 |

공통 source의 고정 revision·원본 hash·라이선스는 [편입 기록](../implementation/ui-component-integration.md)을 따른다. 새 registry 항목의 존재·검수 상태는 아직 확인하지 않았다. [구조 검토 시안](prototype/mobile-workspace.html)은 HTML/CSS로 **모양과 흐름만 시뮬레이션**하며 실제 `ui.pydemia.ai` 컴포넌트·API·권한 동작이 아니다.

## 구현 순서와 수용 조건

1. **깨짐과 탐색:** 실제 운영/로컬 모바일에서 재현 화면을 캡처하고 320·360·390·430 CSS px, 짧은/긴 화면, 태블릿·1440px 기준선을 만든다. 프로젝트·전역 탐색과 상세의 한 pane 전환부터 적용한다. 기존 데스크톱 사이드바와 URL은 보존한다.
2. **매일 쓰는 흐름:** Today/Inbox/빠른 추가·상세·필터 sheet와 키보드/안전 영역을 구현한다. 같은 작업의 planned/due 의미와 완료 gate를 API에서 재검증한다.
3. **정교 작업:** 한 열 보드, 메뉴 이동, 다중 선택 하단 행동, 캘린더 agenda, 집계 1열, 개인 저장 보기의 모바일 접근을 구현한다.
4. **나머지 업무:** 기획/문서/테스트/추적/스킬 작업의 목록→상세와 임시 Markdown 편집·충돌 복구를 구현한다. 모드·테마·긴 콘텐츠 검증 후 릴리즈 판단을 남긴다.

| ID | 관찰 가능한 수용 조건 |
|---|---|
| AC-52 | 320~430px에서 프로젝트 전환·4개 하단 목적지·더보기의 6개 업무 화면에 접근 가능. 본문 첫 화면에 현재 과업과 기본 행동이 보이고 전역 페이지 넘침이 없다 |
| AC-53 | 모바일 Today/Inbox에서 생성→오늘 계획→완료/연기 후 새로고침에도 같은 작업 ID와 planned/due 의미가 유지된다. 구현 작업 완료 gate는 그대로다 |
| AC-54 | 한 열 보드에서 다섯 상태로 선택·이동, 열 안 순서 변경, 현재 열 빠른 생성과 실패/되돌리기를 터치 메뉴만으로 수행할 수 있다. 실제 터치 드래그는 별도로 검증한다 |
| AC-55 | 모바일 다중 선택·일괄 변경에서 대상 수/숨겨진 선택을 알 수 있고 전체 성공 또는 전체 거부된다. 409 뒤 선택과 입력이 남는다 |
| AC-56 | 날짜 띠/agenda와 현재 스냅샷 집계가 320px에서 읽히며 실행 예정과 마감을 혼동하지 않는다. 날짜 없는 작업에도 경로가 있다 |
| AC-57 | 기획·임시 문서·테스트·추적·스킬 작업의 목록→상세→뒤로가 이전 위치로 돌아오고 초안·관계·근거·충돌 행동을 잃지 않는다 |
| AC-58 | 21개 출시 UI 모드의 대표 유형과 light/dark/System, 키보드 표시·안전 영역·긴 콘텐츠·320px reflow·터치 목표·포커스 복귀를 실제 브라우저와 가능한 물리 기기에서 확인한다. favicon/head는 기존 릴리즈 검사를 유지한다 |

검증은 **코드/프로토타입 → 로컬 격리 PostgreSQL과 실제 브라우저 → 운영 빌드·Entra 로그인 → 물리 기기**로 구분한다. 첫 단계의 시안만으로 AC-52~58을 완료 처리하지 않는다. 모바일/데스크톱은 같은 계정·프로젝트·작업을 열어 URL·revision·선택·필터·저장 보기가 기기 전환에도 동일한지 대조한다. 운영 반영은 별도 실행·검증 결정이다.

## 2026-10-22 구현 반영

로컬 앱에는 공통 `BottomNav`·`Dialog`와 기존 작업/문서 API를 결합한 모바일
탐색·시트·한 화면 상세, 한 열 보드와 상태/순서 메뉴, 주간 날짜 agenda,
추적 관계 행을 적용했다. `320·360·390·430px`과 1440px에서 실제 앱의
PostgreSQL 저장을 브라우저로 확인한 근거는 [검증 기록](../implementation/verification.md)에
있다. 이 기획의 보드 열 스와이프, 실제 물리 기기 터치 드래그, 모바일
Markdown 전용 탭과 OS 키보드·안전 영역 실측은 아직 구현/검증을 구분해야
한다. 상태 선택기·메뉴, 기존 편집/미리보기 탭은 대체 경로로 동작한다.
